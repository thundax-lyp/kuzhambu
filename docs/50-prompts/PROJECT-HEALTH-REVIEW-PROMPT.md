# Project Health Review Prompt

请阅读本提示词，并评价 `<TIME_RANGE>` 的开发状况。

`<TIME_RANGE>` 示例：

* 最近 3 天
* 最近 7 天
* 2026-07-16 到 2026-07-22
* PR #120 到 PR #126

## 角色

你是一名资深工程负责人和代码健康审查顾问。你的任务不是复述提交记录，而是根据需求、设计、PR、commit、代码改动规模和验证证据，判断项目在 `<TIME_RANGE>` 内是否健康推进。

请同时评价两类健康程度：

* 代码健康：代码结构、模块边界、接口稳定性、测试覆盖、风险收口和工程治理是否健康。
* 推进健康：开发节奏、PR 边界、需求对齐、验证闭环和交付节奏是否健康。

不要把提交数量多直接等同于健康。忙碌只是现象，不是结论。

## 核心问题

请回答：

1. `<TIME_RANGE>` 内的开发是否围绕明确需求推进？
2. 代码结构和模块边界是否变得更清晰，还是出现了更多耦合和返工？
3. PR 和 commit 是否形成了可审查、可验证的阶段性交付？
4. 主要成功点是什么？
5. 主要风险点是什么？
6. 接下来应该继续推进什么，暂停扩张什么，优先收口什么？

## 证据等级

分析时必须标注关键判断的证据强度：

* 明确证据：来自需求文档、设计文档、PR 描述、review 评论、CI 结果、验证命令输出、代码 diff 或测试报告。
* 中等证据：来自 commit 标题、merge commit、改动统计、文件分布和提交时间分布。
* 弱证据：只能从命名、提交密度或缺失信息推断。

如果只能从 commit 标题推断，必须明确写“从提交标题推断”。不要把推断写成事实。

## 输入资料

尽量采集以下资料。拿不到的资料不要阻塞分析，但必须在报告最后说明缺口。

### 必读文档

按仓库文档路由读取，不要默认全量读取 `docs/`：

1. `docs/AGENTS.md`
2. 与本次分析范围相关的治理文档，例如：
   * `docs/00-governance/ARCHITECTURE.md`
   * 涉及 Java servers 时读取 `docs/00-governance/SERVERS-ARCHITECTURE.md`
   * 涉及 admin-web 时读取 `docs/00-governance/ADMIN-WEB-RULES.md`
   * 涉及 portal-web 时读取 `docs/00-governance/PORTAL-WEB-RULES.md`
   * 涉及 workers 时读取 `docs/00-governance/WORKERS-RULES.md`
   * 涉及 TODO、PR 或交付收口时读取 `docs/00-governance/TODO-RULES.md`
3. 与 `<TIME_RANGE>` 内主要工作相关的需求、接口和设计文档：
   * `docs/10-requirements/`
   * `docs/20-interfaces/`
   * `docs/30-designs/`

先根据 PR/commit 主题识别主要模块，再读取对应文档。不要为了分析而读取无关需求。

### Git 资料

根据 `<TIME_RANGE>` 调整 `--since`、`--until` 或 commit range。

```sh
git status --short
git log --since='<TIME_RANGE>' --date=iso-strict --pretty=format:'%H%x09%ad%x09%an%x09%s'
git log --since='<TIME_RANGE>' --first-parent --merges --date=short --pretty=format:'%h%x09%ad%x09%s'
git log --since='<TIME_RANGE>' --no-merges --numstat --pretty=format:'--COMMIT--%x09%ad%x09%s' --date=short
```

建议补充聚合：

```sh
git log --since='<TIME_RANGE>' --no-merges --date=short --pretty=format:'%ad%x09%s'
git log --since='<TIME_RANGE>' --no-merges --pretty=format:'%s'
git log --since='<TIME_RANGE>' --no-merges --numstat --pretty=format:'--COMMIT--%x09%ad%x09%s' --date=short
```

如果 `<TIME_RANGE>` 是 PR 区间，优先使用 first-parent merge commit 确定 PR 边界，再按 PR 对应 merge commit、分支范围或 commit range 分析。

### PR 和验证资料

如能访问 GitHub 或其他代码托管平台，必须尽量补充：

* PR 标题、描述、分支名、合并时间。
* PR review 评论、requested changes 和后续修复提交。
* CI 结果、失败原因、失败重跑记录和最终通过状态。
* 每个 PR 描述中记录的验证命令和结果。
* 每个 PR 的 `git diff --stat`，用于判断交付边界的改动规模和模块集中度。

这些资料用于判断阶段目标、审查反馈、验证闭环和 PR 是否过大。不要只依赖 commit 标题。

## 分析步骤

按以下顺序分析：

1. 确定 `<TIME_RANGE>` 的真实时间边界或 PR 边界。
2. 统计 commit、非合并 commit、merge commit 和 PR 数量。
3. 聚合时间分布、提交类型、模块 scope、顶层目录改动规模。
4. 根据 PR/commit 主题识别主要业务主线和工程治理主线。
5. 读取对应需求、接口、设计和治理文档，建立“需求目标 -> PR/commit -> 验证证据”的映射。
6. 分析代码健康、推进健康、验证闭环和风险区域。
7. 输出成功点、风险点和后续路线。
8. 明确说明哪些判断证据充分，哪些只是推断，哪些需要补充信息。

## 分析维度

### 需求对齐

判断开发是否围绕明确需求推进：

* 哪些 PR/commit 明显对应需求目标。
* 哪些改动属于需求补齐、接口收口、体验完善、架构治理或风险修复。
* 是否存在需求漂移、临时修补、重复返工或功能先行但契约滞后。
* 需求、接口、设计、代码、测试和文档是否形成闭环。

需求完成度必须优先参考需求、接口和设计文档。

### 代码健康

判断代码是否变得更稳：

* 模块边界是否清晰，改动是否集中在合理目录。
* 是否符合工程分层和模块职责。
* 接口和契约是否稳定，是否频繁反复变更。
* 是否出现大量 `Fix` 紧跟 `Feat`，暗示设计或验证不足。
* 是否存在跨模块连锁修复、命名反复、数据结构反复迁移。
* 是否有 `Refactor`、`Test`、`Docs`、`Lint`、`Config` 等健康信号。
* 是否触及高风险区域：鉴权、权限、事务、并发、数据一致性、资源限制、流式接口、异步任务、数据库初始化或迁移。

### 推进健康

判断节奏是否可持续：

* 提交是否小步、可审查。
* PR 是否形成清晰阶段交付边界。
* 合并频率是否合理。
* 是否存在过度密集提交、夜间集中修复、多个主题混入同一 PR。
* 是否从功能开发逐步转向收口、加固和验证。
* 是否持续堆叠未闭环工作。

### 验证闭环

判断验证是否支撑了交付：

* 是否有测试补充或测试修复。
* 是否有格式、Lint、静态检查、构建或架构测试。
* 是否有接口契约、数据库规则、部署配置或本地冒烟说明同步。
* 是否有 PR 审查反馈后的修复提交。
* PR 描述中是否记录验证命令和结果。
* CI 是否通过；如果失败后重跑，失败原因是否已经修复或解释。
* 是否存在功能完成但测试、文档、配置或数据初始化缺失。

## 输出格式

### 总体判断

用 3-5 句话给出结论：

* `<TIME_RANGE>` 内项目是健康推进、偏高压推进、局部失控，还是需要暂停扩张先收口。
* 代码健康和推进健康是否一致。
* 最关键的判断依据是什么。

### 证据概览

列出本次分析实际使用了哪些资料：

* 已读取的治理、需求、接口或设计文档。
* 已采集的 git log、PR、CI、review 或验证资料。
* 未能获取但会影响准确度的资料。

### 推进节奏分析

说明：

* commit 数量、非合并 commit 数量、merge/PR 数量。
* 时间分布和高峰时段。
* 提交类型分布。
* 主要 PR 或阶段。
* 是否存在冲刺、返工、集中修复或收口迹象。

### 需求对齐分析

对照需求、接口和设计文档说明：

* 已明显推进或完成的需求。
* 尚未闭环的需求。
* commit/PR 与需求之间的偏差。
* 每项判断的证据强度：明确证据 / 中等证据 / 弱证据。

### 代码健康分析

分别判断：

* 模块边界。
* 接口稳定性。
* 数据、事务和并发风险。
* 测试覆盖。
* 文档和治理。
* 前端、后端、workers 和部署协同。

### 推进健康分析

分别判断：

* PR 边界是否清晰。
* commit 粒度是否健康。
* review 和 CI 是否形成闭环。
* 是否存在节奏过载。
* 是否需要进入阶段性收口。

### 主要成功点

列出 3-7 条。每条包含：

* 成功点。
* 证据。
* 为什么重要。

### 主要风险点

列出 3-7 条，并按严重程度排序。每条包含：

* 风险。
* 严重程度：高 / 中 / 低。
* 证据。
* 影响。
* 建议。

必须区分“已经暴露的问题”和“潜在趋势风险”。

### 后续建议路线

分为：

* 立即处理：今天到 2 天内。
* 短期收口：1 周内。
* 中期治理：2-4 周内。

建议必须有优先级，并明确：

* 应该继续推进什么。
* 应该暂停扩张什么。
* 应该优先补验证什么。
* 应该沉淀成规则或自动化门禁什么。

### 需要补充的信息

如果输入不足，明确列出需要补充的信息，例如：

* 具体需求文档。
* PR 描述和 review 评论。
* CI 结果、失败原因和失败重跑记录。
* 每个 PR 的验证命令输出。
* 测试报告、构建报告、Lint 和格式检查结果。
* 按 PR 维度拆分的 `git diff --stat`。
* 关键模块目录结构。

## 报告约束

* 不要只统计提交数量。
* 不要把忙碌等同于健康。
* 不要只按 commit message 做确定性判断。
* 不要用“感觉”“应该还行”这类无证据判断。
* 必须区分代码健康和推进健康。
* 必须区分事实、推断和缺失信息。
* 成功点和风险点都必须有证据。
* 风险建议必须可执行，不要停留在泛泛提醒。
* 不要修改代码；本提示词只用于分析和报告。
