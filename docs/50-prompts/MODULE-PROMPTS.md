# Module Code Review Prompt

请对模块 `<MODULE_PATH>` 的全部代码进行一次系统性 Code Review。

目标：

* 审查该模块当前全部代码，而不是只审查最近的 Git 变更。
* 重点发现真实缺陷、架构问题、维护风险和可简化之处。
* 不要直接修改代码，只输出审查报告。

## 一、审查边界

主要审查范围：

`<MODULE_PATH>`

请先完成以下工作：

1. 列出该模块的目录结构。
2. 识别模块入口、核心类、公共接口、主要数据流和依赖关系。
3. 阅读模块内全部源代码、配置文件和测试代码。
4. 必要时可以读取其他模块的代码，以理解接口、调用关系和数据结构。
5. 外部模块只作为上下文，不对其进行全面审查。
6. 忽略生成文件、构建产物、第三方依赖和压缩文件。

## 二、重点检查

### 1. 正确性

检查：

* 逻辑错误。
* 边界条件遗漏。
* 空值、空集合和非法状态处理。
* 异常处理不完整、异常被吞掉或错误转换。
* 状态不一致。
* 生命周期和资源释放问题。
* 并发、线程安全、竞态条件和重复执行问题。
* 潜在的数据丢失、覆盖或污染。
* 时间、时区、精度、编码和序列化问题。

只报告能够说明触发条件和实际影响的问题。

### 2. 模块职责与架构

检查：

* 模块职责是否清晰。
* 模块是否承担了不属于自己的职责。
* 包结构和目录结构是否合理。
* 依赖方向是否正确。
* 是否存在循环依赖。
* 是否存在跨层调用。
* 领域逻辑、应用逻辑和基础设施逻辑是否混杂。
* 公共接口是否稳定、最小且清晰。
* 内部实现是否被不必要地暴露。
* 抽象层级是否过多或不足。
* 是否存在为了抽象而抽象的接口、工厂、包装类或中间层。

### 3. 文件与包结构

检查：

* 文件名是否准确表达职责。
* 文件路径是否符合代码所属层级。
* 类是否放在正确的包中。
* 一个文件或类是否包含多个无关职责。
* 是否存在内容过少、没有独立价值的文件。
* 是否存在应该拆分但过度膨胀的文件。
* 包名、目录名和实际职责是否一致。

### 4. 命名

检查：

* 模块名、包名、文件名、类名、方法名、属性名和变量名。
* 命名是否准确表达真实语义。
* 是否存在模糊名称，例如 `data`、`info`、`manager`、`handler`、`util`、`process`。
* 是否存在名称与实际行为不一致。
* 是否存在同一概念使用多个不同名称。
* 是否存在布尔值、集合、命令和查询命名不清的问题。
* 是否存在不必要的缩写或过长名称。

命名问题必须给出更合适的建议名称。

### 5. 清晰性与简洁性

检查：

* 重复代码。
* 重复条件判断。
* 重复的数据转换。
* 不必要的包装方法。
* 无价值的接口或抽象类。
* 过深的调用链。
* 过深的嵌套。
* 不必要的中间变量和临时对象。
* 可以合并的相似实现。
* 可以删除的死代码、废弃代码和未使用代码。
* 可以简化但不会损害可读性或扩展性的代码。

不要为了减少代码行数而牺牲语义清晰度。

### 6. API 与封装

检查：

* 公共 API 是否过多。
* 方法参数是否过多。
* 返回值是否难以理解。
* 是否使用不明确的 Map、Object、数组或字符串传递结构化数据。
* 可变状态是否被直接暴露。
* 是否缺少必要的不可变约束。
* 调用方是否必须了解过多内部实现。
* 接口是否容易被误用。
* 默认值、失败语义和异常约定是否明确。

### 7. 性能与资源

检查：

* 明显的重复计算。
* 不必要的 I/O。
* 循环中的数据库、网络或文件操作。
* 无界集合、缓存或队列。
* 不合理的全量加载。
* 大对象复制。
* 阻塞操作。
* 线程池、连接、流和文件句柄未正确释放。
* 明显的 N+1 调用。
* 会随数据规模显著恶化的算法。

不要报告没有实际依据的微优化。

### 8. 安全性

检查：

* 输入校验缺失。
* 权限校验缺失。
* 路径遍历。
* 命令、SQL、模板或表达式注入。
* 不安全反序列化。
* 敏感数据日志输出。
* 密钥、Token 或密码硬编码。
* 不安全的随机数或加密方式。
* 用户输入直接控制文件、网络或执行行为。

### 9. 测试

检查：

* 核心行为是否有测试。
* 失败路径是否有测试。
* 边界条件是否有测试。
* 测试是否只验证实现细节。
* 测试是否存在重复、脆弱或不可读的问题。
* 测试名称是否准确。
* Mock 是否过多，导致测试失去实际价值。
* 是否缺少模块级集成测试。
* 是否存在实现已经变化但测试未同步的问题。

## 三、报告原则

* 只报告明确、可操作、值得修改的问题。
* 不要为了凑数量而提出建议。
* 不报告单纯的代码格式问题。
* 不把个人风格偏好描述为缺陷。
* 不确定的问题明确标记为“需要确认”。
* 相同根因的问题合并。
* 每个问题都必须给出具体文件和代码位置。
* 优先报告正确性、回归风险、架构和接口问题。
* 对于结构性问题，说明它影响了哪些文件或调用链。
* 不要只描述“代码复杂”，必须说明复杂在哪里以及如何降低复杂度。

## 四、输出格式

先输出：

# Module overview

包括：

* 模块主要职责。
* 目录和包结构概述。
* 核心入口。
* 核心类和接口。
* 主要数据流。
* 外部依赖。
* 对外暴露的 API。
* 当前测试覆盖概况。

然后逐条输出问题：

## [P0/P1/P2/P3] 问题标题

* 类型：正确性 / 架构 / 结构 / 命名 / 简化 / API / 性能 / 安全 / 测试
* 文件：`文件路径`
* 行号：具体行号或最小代码范围
* 问题：问题的具体内容。
* 触发条件：在什么情况下出现。
* 影响：可能造成的实际后果。
* 原因：问题产生的根本原因。
* 建议：具体、可执行的修改方向。
* 关联范围：受影响的类、接口或调用方。

优先级：

* P0：可能造成严重安全事故、数据损坏或系统不可用。
* P1：高概率导致明确错误、严重回归或核心架构失控。
* P2：真实存在的局部缺陷或重要维护问题。
* P3：低风险但值得处理的结构、命名或简化问题。

最后输出：

# Refactoring priorities

按照投入产出比排序，列出最值得优先处理的 5-10 项。

每项包括：

* 修改目标。
* 涉及文件。
* 预期收益。
* 风险。
* 建议拆分步骤。

最后输出：

# Review summary

* 是否存在阻断性问题。
* P0 数量。
* P1 数量。
* P2 数量。
* P3 数量。
* 模块整体评价。
* 最大正确性风险。
* 最大架构风险。
* 最值得优先简化的部分。
* 测试覆盖的主要缺口。

如果没有发现值得报告的问题，明确输出：

`No actionable findings.`

注意：先建立模块结构和调用关系，再按包逐个审查；不要只抽样阅读核心文件。
