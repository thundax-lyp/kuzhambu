# PR Code Review Prompt

请对当前分支相对于 `main` 分支的代码变更进行一次严格的 Pull Request Review。

审查范围：

* 使用 `git diff main...HEAD` 确定本次变更。
* 阅读必要的上下文代码，但只报告由本次变更引入或暴露的问题。
* 不要修改代码，只输出审查结果。

重点检查：

1. 正确性

* 逻辑错误、边界条件遗漏、空值处理错误。
* 异常处理不完整或错误被吞掉。
* 并发、状态同步、生命周期和资源释放问题。
* 是否破坏已有功能或向后兼容性。

2. 架构与结构

* 文件名和文件路径是否准确、清晰。
* 包结构、模块职责和依赖方向是否合理。
* 是否存在职责混乱、循环依赖或不必要的抽象。
* 新增代码是否放在了正确的层级和模块中。

3. 命名与可读性

* 类名、方法名、属性名、变量名是否准确表达语义。
* 是否存在模糊、冗余、误导或不一致的命名。
* 代码是否可以在不损害功能的前提下进一步简化。
* 是否存在重复逻辑、无效封装或不必要的中间层。

4. 安全性与稳定性

* 输入校验、权限检查、敏感信息泄露。
* 注入、路径遍历、不安全反序列化等风险。
* 潜在的性能退化、内存泄漏或阻塞操作。

5. 测试

* 新增行为是否有测试覆盖。
* 测试是否覆盖失败路径、边界情况和回归风险。
* 测试是否真正验证行为，而不是只验证实现细节。

报告规则：

* 只报告明确、可操作、值得开发者修改的问题。
* 不要报告纯格式问题，除非它明显影响理解或维护。
* 不要为了凑数量而提出建议。
* 不确定的问题不要描述为确定缺陷。
* 相同根因的问题合并报告。
* 优先报告 bug、回归风险和架构问题，而不是个人风格偏好。

每个问题使用以下格式：

### [P0/P1/P2/P3] 简短标题

* 文件：`路径`
* 行号：具体行号或最小代码范围
* 问题：说明哪里有问题。
* 影响：说明在什么情况下会发生，以及可能造成什么后果。
* 建议：给出简洁、具体的修复方向。

优先级定义：

* P0：必须立即修复，会导致严重事故、安全漏洞或数据损坏。
* P1：高概率造成明显错误或严重回归。
* P2：真实存在但影响范围有限的问题。
* P3：低风险的维护性或结构性问题。

最后输出：

## Review summary

* 是否建议合并：是 / 修复后合并 / 不建议合并
* P0 数量
* P1 数量
* P2 数量
* P3 数量
* 最主要的风险概述

如果没有发现值得报告的问题，明确输出：

`No actionable findings.`

先执行并阅读 `git status`、`git diff --stat main...HEAD` 和 `git diff main...HEAD`，然后开始审查。
